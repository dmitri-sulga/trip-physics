# Method

This is the long version of the README: what the detector looks at, how the
harness measures it, the reporting rules, the held-out false-positive check,
how to run it on real logs, and the limits. Every figure below names the
command that produces it; all of them describe the synthetic generator in
`src/tripphysics/synth.py`, not real traffic.

## The detector

One driver account, several people driving on it. `features.py` turns an
account's trip log into eleven features (in-trip jumps beyond 250 km/h,
reported speed and acceleration, GPS jitter, the OS mock-location flag, GPS
position against the serving cell, the distance an account "teleports" between
the end of one trip and the start of the next, overlapping trips, two driving
styles on one account, night share, and the share of unparseable fixes).
`detector.py` turns them into one score: a weighted sum of monotone evidence
terms with named constants, squashed to [0, 1]. There is no fitted model.

## The U metric

Recall comparisons are meaningless without a fixed alert budget, so the budget
comes first:

- **Budget** — B flagged honest accounts per 10,000 honest accounts (default
  B = 50, i.e. 0.5%). The demo also reports U at B ∈ {15, 30, 50, 100, 200},
  so the operating point is visible rather than picked after the fact.
- **R0** — recall on shared accounts using the baseline scorer alone.
- **R1** — recall using the baseline **stacked** with this detector (called
  `pilot` in code and in JSON keys).
- **U = (R1 − R0) / R0** — relative recall gain at the same _realized_ FP
  spend. The budget names a maximum; both scorers are measured at the largest
  spend a strict threshold reaches on both of them, so a coarse baseline cannot
  underspend the budget and inflate U (see CHANGELOG, 2026-08-03). The report
  prints that realized spend and the budget utilization next to U.

Stacking rule (inside `evaluate()`):
`stacked = max(rank(baseline), rank(detector))` — each score is rank-normalized
within its own population (ascending rank / n, ties averaged), then the
per-account max is taken. `max` means the detector can only add candidates to
the queue, never bury a baseline alert. Detector false positives spend budget
too, so stacking _can_ push R1 below R0; that would be a real result.

Also reported: hand-written PR-AUC (trapezoid over the precision-recall
curve; one open defect, see [Limits](#limits)) and precision@500 for both
scorers, plus the chosen thresholds.

## What the synthetic U is, and the acceptance bar for real data

On the synthetic data the generator and the detector were written by the same
person, so the detector's assumptions are true by construction, and the
baseline (`NaiveBaseline` in `baseline.py`) is a deliberately crude stand-in.
The synthetic U therefore checks that the measurement works end to end. It is
not an estimate of what the detector would add on real data, and it should not
be quoted as one.

For a run on real logs, the bar is fixed before the run: **U ≥ +20% at the same
realized false-positive spend**, with a bootstrap 95% CI and at least 150
confirmed positives in the window (`report.U_TARGET`). The synthetic demo never
renders a verdict against it:

|              | synthetic demo                                        | run on real logs                                 |
| ------------ | ----------------------------------------------------- | ------------------------------------------------ |
| data         | generated by `synth.py`                               | a real shadow log                                |
| labels       | true by construction                                  | confirmed cases, incomplete                      |
| what U means | the pipeline computes the metric correctly end to end | whether the detector adds recall on that traffic |
| verdict      | none — none is possible                               | against U ≥ +20%                                 |

I tuned the generator until the demo showed a plausible but imperfect result,
because a perfect number would only show that I had overfit my own simulator.
The synthetic median (+15.5%) sits below the +20% bar, and the demo says so
rather than searching for a configuration that clears it.

## Reporting rules

Three rules, each there because breaking it is how offline evaluations flatter
themselves.

**1. The headline is a median across seeds, never a single seed.** One seed is
one draw from a distribution of synthetic worlds. `run_demo.py` sweeps seeds,
prints median / mean / sd / min / max, and leads with the median. The seed in
the detailed tables is the first one, labelled as a worked example. (The
CHANGELOG records the single-seed headline this rule replaced.)

**2. U carries a bootstrap 95% CI.** `eval.bootstrap_uplift_ci()` resamples
accounts with replacement, stratified so each replicate keeps the observed
shared/honest counts, and re-derives the threshold on every replicate, so
threshold-choice variance lands inside the interval.

<a id="sample-size"></a>

**3. The population is large enough for U to mean anything.** At 2,000
accounts and a 3% base rate there are 60 positives. Measured across seeds
1..K (`python examples/sample_size_table.py`; the 20,000 row is the committed
`--full` sweep):

| accounts | positives | seeds | median U | sd of U   | range           |
| -------- | --------- | ----- | -------- | --------- | --------------- |
| 2,000    | 60        | 25    | +16.7%   | 7.5pp     | +2.5% … +37.5%  |
| 5,000    | 150       | 10    | +17.0%   | 7.5pp     | +8.3% … +30.9%  |
| 8,000    | 240       | 10    | +16.7%   | 4.7pp     | +6.1% … +21.1%  |
| 20,000   | 600       | 20    | +15.5%   | **2.0pp** | +12.9% … +19.9% |

The median barely moves across all four rows — it stays between +15.5% and +17.0%.
The spread is what changes. That is the whole finding: **the sample size was
the story, not the detector.** At 2,000 accounts a single seed could return
anything from +2.5% to +37.5%, so any single-seed headline from that
configuration reported mostly luck. The demo therefore defaults to 20,000
accounts and leads with a median.

## The held-out false-positive check


The threshold is calibrated on the same honest
population it is measured on, so in-sample the realized FP rate matches the
budget by construction — that is a tautology, not evidence. Since the budget
is a _promise_ about how many honest drivers get flagged, the demo also runs
`eval.holdout_fp_check()`: threshold fitted on half the honest accounts, FP
rate measured on the other half.

The shipped 20,000-account run reports a single split (`seed=0`): 46.4/10k for
the baseline and 70.1/10k for the stacked scorer, against a 50/10k budget. **That pair
is not a property of the scorers.** Re-running the same check across 20 split
seeds on the same population (`python examples/holdout_split_sweep.py`):

| scorer   | budget   | median held-out rate | range over 20 splits |
| -------- | -------- | -------------------- | -------------------- |
| baseline | 50 / 10k | 44.3 / 10k           | 30.9 … 69.1 / 10k    |
| stacked  | 50 / 10k | **49.5 / 10k**       | 24.7 … 70.1 / 10k    |

The stacked scorer's median lands on the budget, not 40% over it, and the shipped
`seed=0` value of 70.1 is the **highest of the 20 splits** — the next one down
is 58.8. Re-drawing the population instead of the split tells the same story
over 8 population seeds (`python examples/holdout_population_sweep.py`):
the shipped `seed=1` is again the maximum, the median
is 47.4/10k, and on five of the eight the stacked scorer spends _no more_ than the
baseline — the sign of the effect flips. Nor is the gap separable:
`eval.holdout_fp_budget_ci()` puts a stratified bootstrap interval around each
rate, and they overlap on 53.6 … 74.2 — baseline [30.9, 74.2], stacked
[53.6, 93.8]. A claim that the stacked scorer systematically overspends does not follow
from one split.

The noise is countable, not mysterious. The split leaves 9,700 honest accounts
in the measurement half, so a 50/10k budget expects 9,700 × 50/10,000 = 48.5
flags. Poisson counting noise alone is √48.5 / 48.5 = **±14%**, and on top of
that the threshold itself is fitted on the other 9,700 accounts, so
threshold-selection variance adds to it. Spread of this width is what the
measurement is made of at this size. It does shrink as the honest population
grows, but only as 1/√N, because a budget stated as a rate allows more flags in
a larger population: over 200 splits of the same population, the relative
spread of the stacked scorer's held-out rate falls from 52.8% at 2,425 honest
accounts to 18.1% at 19,400, following √(2 / expected flags)
(`python examples/holdout_spread_vs_n.py`). Halving it again takes four times
the accounts: about 80,000 honest accounts for ±10% and 320,000 for ±5%. At the
sizes in this repository one split is therefore not a quotable number.

This is the instrument working, not a defect in it: a budget promise read off
one split is exactly the kind of number this harness exists to refuse. Read
the held-out FP rate through `eval.holdout_fp_budget_ci()`, which returns the
interval, rather than through a point estimate. On real data, calibrate on a
window that _precedes_ the measurement window.

## Running it on real logs

1. Export driver-side trip fixes as JSONL — ten fields, defined in
   [`schema/input_schema.md`](../schema/input_schema.md). No personal data, no
   rider data, no payment data.
2. Export the current scorer's per-account scores as `account_id,score` CSV.
   Comma-separated, UTF-8, `.` as the decimal point. Semicolon or tab
   delimiters and decimal commas (`0,73`) are rejected with a message naming
   the line, because a spreadsheet export that writes `0,73` would otherwise
   truncate every score to `0`.
3. Collect labels for the window: which accounts were confirmed shared.
4. Run:

```python
from tripphysics.baseline import load_scores_csv
from tripphysics.detector import score_account
from tripphysics.eval import evaluate
from tripphysics.features import extract_features
from tripphysics.report import render_report

accounts = ...  # the JSONL, grouped per schema/input_schema.md
labels = ...    # {account_id: confirmed_shared_bool}

base = load_scores_csv("production_scores.csv")
det = {a["account_id"]: score_account(extract_features(a)) for a in accounts}

# evaluate() stacks base and det internally
result = evaluate(labels, base, det, budget_fp_per_10k=50.0)
render_report(result, {"window": "2026-10"}, "out/report.json", "out/report.md")
```

Everything runs locally, and the report holds aggregate metrics only. The
Docker image runs with `--network=none` (see [running.md](running.md)), so
the absence of network access is enforced by the runtime.

To measure an existing score column without trip data at all, use the
bring-your-own-scores command: [byos-guide.md](byos-guide.md).

## Limits

- **Synthetic data shows that the harness works, not that the detector works
  on real traffic.** The synthetic sharing patterns were designed alongside the
  detector; on real trips base rates and evasion behaviour will differ.
- R0, R1 and U are only as good as the labels. Sparse or noisy confirmed-shared
  labels bias both recalls; the report states label counts.
- The detector targets the physically implausible tail of sharing. A pattern
  that is physically clean — same household, phone handed over at home,
  similar driving styles — will not trip it.
- With small honest populations the FP budget quantizes hard (15/10k of 5,000
  accounts is 7 alerts); see the sample-size table above.
- The threshold is calibrated on the same honest population it is measured
  on; the held-out check above sizes that gap.
- One detector, one abuse type. This is a measurement harness plus one
  focused signal, not a fraud platform.
- **One open defect in the metric code.** With every score tied, `pr_auc`
  returns (1 + base rate) / 2 instead of the base rate; more generally the
  (0, 1) anchor over-credits a top group of tied scores that contains honest
  accounts. It is pinned by the one expected failure in the suite
  (`tests/test_metric_edge_cases.py`) and described in the `pr_auc`
  docstring. It does not affect the committed report, whose top groups are
  pure, and the bring-your-own-scores command refuses a constant score column.
- **Known evasion vectors.** These are properties of the current scoring, not
  hypotheticals, and each is cheap for an attacker. The full list, with
  measured verdicts, is [`attacks/ATTACKS.md`](../attacks/ATTACKS.md).
  - _Volume dilution._ `handover_gap_score` is the **mean** over consecutive
    inter-trip gaps, so appending geometrically clean filler trips lowers it
    without removing the original handover (registry entries
    `vol-dilution-25` and `vol-dilution-100`, recorded but not re-runnable
    here). `night_share`, `mock_rate` and `cell_mismatch_rate` are rates and
    dilute the same way. A max or a high quantile would resist this; the mean
    is what ships today.
  - _Client-reported fields._ `max_speed_kmh` and `accel_p99_ms2` come from
    the reported `speed_mps` field and are never cross-checked against
    position over time, so self-consistent falsified speeds defeat both.
    Likewise `is_mock` and `cell_id` are taken verbatim from the client.
    In a real deployment `cell_id` must come from an operator-side tower
    join; in this synthetic world it is a pure function of x/y, so it is
    trivially forgeable here.
  - _Bridging._ Handover excess is scored only between _consecutive_ trips,
    so inserting one plausible intermediate trip splits a large spatial jump
    into two explainable legs.
  - _Silence._ An account with no usable trips yields the all-zero vector and
    is mapped to a hard 0.0, the minimum score. That is deliberate ("absence
    of evidence is not evidence of innocence"), but it does mean that in pure
    ranking terms, submitting nothing sorts below every honest account.
    Empty accounts belong in their own queue, not at the bottom of this one.
